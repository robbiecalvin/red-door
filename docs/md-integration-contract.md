# Red Door × Meet Discreet integration contract — v1

This is the contract the **Meet Discreet environment must implement**. Red Door's implementation is in `backend/src/services/mdBridge.ts`. No MD production service has been contacted or configured by this work.

## Hosts and configuration

- Red Door app after domain purchase: `https://thereddoor.app/`.
- MD app: `https://meetdiscreet.ca/`.
- App domains and backend/API domains are separate. The current Red Door API is `https://red-door-api.onrender.com`; the static Pages app cannot receive server API calls.
- On Red Door, set `MD_API_BASE_URL` to the MD backend's API base, `MD_SITE_URL=https://meetdiscreet.ca`, and `MD_SHARED_SECRET` to a shared random secret of at least 32 characters.
- Configure **the same MD_SHARED_SECRET on both backends only**. Never put it in a browser bundle, public repository, or URL. Generate a value in your deployment platform's secret manager, then configure both environments.
- MD images must be HTTPS URLs on meetdiscreet.ca, or a host explicitly listed in Red Door's `MD_MEDIA_ALLOWED_HOSTS`. MD can serve a photo proxy under its own domain.
- Red Door account keys are generated by Plus members, shown once, and stored only as keyed hashes. They are independent of the shared service secret and of Red Door passwords. Rotation invalidates the old link. Disconnecting is allowed even after Plus expires.

## Signed JSON requests (both directions)

All integration endpoints use POST JSON and these headers:

```
X-MD-Timestamp: <Unix seconds>
X-MD-Nonce: <new UUID or random 16–100-character token>
X-MD-Signature: <lowercase hex HMAC-SHA256>
```

Sign the following UTF-8 string, joined with newlines and **no trailing newline**:

```
timestamp
nonce
POST
/logical/endpoint/path
sha256(raw JSON body bytes as UTF-8).hex
```

The logical path excludes the backend API-base prefix. For example, posting to `https://meetdiscreet.ca/api/integrations/red-door/chat/redeem` signs `/integrations/red-door/chat/redeem`. Preserve the exact JSON bytes that were signed. Red Door accepts up to five minutes of clock skew and rejects replayed nonces. Retries use a fresh nonce. Do not log account keys or paid-chat codes.

Every MD call must also enforce the currently authenticated MD user/provider's ownership, paid status, adult verification, and publication/moderation status on MD. A browser must never send trusted service assertions directly to Red Door.

## 1. Link a provider (MD → Red Door)

Only show MD's “I also have Red Door Plus” checkbox for an authenticated provider with a paid, published/live MD profile. Submit the entered Red Door email/key from the MD backend:

`POST /integrations/md/link`

```json
{"email":"provider@example.com","key":"rd_link_...","providerId":"md-provider-id","paid":true,"liveProfile":true,"adultVerified":true,"paidUntilMs":1800000000000,"name":"Provider display name","photoUrl":"https://meetdiscreet.ca/photos/provider.jpg","profileUrl":"https://meetdiscreet.ca/providers/md-provider-id","lat":49.28,"lng":-123.12}
```

Coordinates must be an approximate, provider-consented service area, not an undisclosed residence. Red Door coarsens them further and returns only distance bands to viewers. Responses never expose the linked Red Door provider's private account ID.

Response: `{"linked":true,"redDoorPlus":true,"linkId":"opaque-id","providerId":"md-provider-id"}`. Store linkId on the MD provider. Red Door verifies the matching email/key, adult account status, and active Plus. One provider is linked per Red Door account and a provider cannot silently be reassigned to someone else.

`POST /integrations/md/status` with `{linkId,providerId}` returns `{linked,redDoorPlus,liveUntilMs}`. Show MD's green “Go Live on Red Door” affordance only while this confirms active linking.

## 2. Go live / offline (MD → Red Door)

`POST /integrations/md/live` with `{linkId,providerId,active:true,...the current paid/profile/photo/location assertions from linking}`.

Response: `{live:true,liveUntilMs}`. MD must refresh live status **at least every five minutes while the provider has chosen to be live**. Red Door expires it within ten minutes, or earlier when either membership ends. Do not automatically make every logged-in provider live without their choice.

To stop: `{linkId,providerId,active:false}`. Also stop/refresh assertions immediately when the MD profile is unpublished, suspended, refunded, or its paid period ends. Red Door independently checks its own account status on every directory/chat request.

## 3. Paid subscriber handoff (Red Door → MD)

A Plus viewer opens a provider using `/md/handoff`. Red Door directs the browser to the provider's MD profile URL with:

- `rd_handoff`: an opaque 30-minute ticket.
- `rd_return`: Red Door's configured app URL ending `/#/md`.

MD's backend verifies the ticket with:

`POST /integrations/md/handoff` → `{ticket,providerId}`.

Response: `{viewerId,providerId,expiresAtMs}`. Bind the MD purchase/account and subsequent chat receipt to this **exact Red Door viewerId and providerId**. Never trust a viewerId supplied by a browser in place of this lookup. If the ticket expired, send the user back to Red Door to open the provider again.

MD creates its own account/follow relationship and collects the provider's $11.99 subscription using MD's existing payment system. **Red Door does not collect that charge and does not unlock chat from a browser success URL.**

## 4. Generate a friendly code after verified MD payment (MD)

Only after MD's backend verifies the successful canonical payment/subscription state, generate and display a code for this buyer/provider and store its hash with the grant. Use memorable multiple words (recommended: six cryptographically selected words from a dictionary of at least 1,024 words), for example `frog-banana-door-mango-lantern-otter`. Single words are guessable. Red Door accepts four to eight lowercase words separated by hyphens or spaces.

Bind the code to `{viewerId,providerId,grantId,paidUntilMs}`. Show/copy it after payment; do not include it in URLs. Regeneration revokes the previous code, but should not revoke an already-paid subscription. If users miss a one-time code, MD needs a secure regenerate action in their paid account.

## 5. Verify/redeem a paid chat code (Red Door → MD)

**MD must implement:** `POST /integrations/red-door/chat/redeem`.

Signed request: `{viewerId,providerId,code}`. Header `Idempotency-Key` is a deterministic digest for this same account/provider/code retry.

MD must verify code ownership, the authenticated handoff binding, current paid subscription and follow entitlement, provider availability/publication eligibility, and no refund/chargeback. A different viewer or provider must be rejected even if they know the phrase. Rate-limit attempts; store only hashes. Code consumption and receipt issuance must be atomic. Identical retries for the same viewer/provider/idempotency key may return the same receipt, never a new entitlement period.

Response:

```json
{"paid":true,"viewerId":"exact-red-door-viewer-id","providerId":"exact-md-provider-id","grantId":"stable-md-subscription-grant-id","expiresAtMs":1800000000000}
```

Failure: 403 with a generic error. Red Door grants access only after this server verification, stores the receipt without the phrase, and never extends beyond the returned paid period. An MD provider going offline does not revoke an already-paid chat period; account suspension, expired memberships, blocks, refunds, or revoked linking do stop access.

## 6. Provider inbox and reply from MD (MD → Red Door)

- `POST /integrations/md/inbox` → `{linkId,providerId}`. Returns `{threads:[{viewerId,expiresAtMs}]}`.
- `POST /integrations/md/messages` → `{linkId,providerId,viewerId}`. Returns authorized text messages.
- Send with the same endpoint plus `{text,clientMessageId}`. clientMessageId must be a unique UUID kept across network retries. Identical retries return the same message; conflicting reuse is rejected.
- A provider can also open their MD inbox from Red Door's MD tab. These conversations are separate from ordinary Red Door chats.
- Messages are text-only, rate-limited, and retained up to 72 hours. Inbox/message access requires the calling account's Plus plus a valid linked provider and paid MD grant. Existing Red Door blocks are honored.
- Provider message identities use an MD alias; Red Door does not expose their linked personal account ID in directory/message payloads.

## 7. Revoke a paid grant (MD → Red Door)

`POST /integrations/md/chat/revoke` → `{grantId,providerId}`. Call on refunds, chargebacks, or other immediate entitlement revocations. Normal cancellation should retain access until the already-paid period ends unless MD's disclosed terms say otherwise. Red Door also rejects expired grants automatically.

## Operational checks

Before live launch, configure both backends and test with staging/test subscriptions: wrong email/key, key rotation, lapsed Plus/MD payment, live/offline timeout, 50-km filtering, subscriber signup/payment/code, wrong viewer/code, replay/idempotent retry, messages from both sites, refund/revocation, and blocking. No actual MD production interoperability is claimed until the MD environment implements and exercises this contract.
